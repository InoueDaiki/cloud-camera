## エッジ

### H.265 をそのまま KVS へ送るパイプライン(2026-10-24)

- 決めたこと: `rtspsrc ! rtph265depay ! h265parse ! video/x-h265,stream-format=hvc1,alignment=au ! h265timestamper ! kvssink`
- 理由: RTSP から取り出したフレームには DTS がなく、kvssink がキーフレームを捨てて断片が 1 つもできなかった。`h265timestamper` で解決。kvssink はコーデックプライベートデータを caps の `codec_data` からしか取らないため `hvc1` の指定が必須
- 構想.md との差: なし(再エンコードしない方針のまま)

### 回線断はメモリのバッファまで(2026-10-24)

- 決めたこと: kvssink のメモリ上のバッファを約 10 分ぶんに設定し、回線断ではパイプラインを再起動しない。ディスクへの退避はしない
- 理由: ディスク退避は録画・再送の仕組みを自前で作ることになり、エッジが厚くなりすぎる。10 分を超える回線断は欠落として許容
- 構想.md との差: 「エッジでバッファリングしない」から、kvssink の既存機能の設定範囲だけ許容に変更

### ライブの低遅延化のためならエッジが少し厚くなってもよい(2026-10-24)

- 決めたこと: KVS WebRTC(シグナリングチャネル)によるライブ配信を調査・試作する。エッジに WebRTC の送信部品が増えるのは許容
- 理由: HLS のライブは数秒遅れ、PTZ の操作感が悪い。低遅延のメリットがエッジの複雑さを上回る
- 構想.md との差: ライブの経路に WebRTC が加わる(調査中。結果は [webrtc.md](webrtc.md))

## クラウドの処理

### 区間の確定はウォーターマーク方式(2026-10-24)

- 決めたこと: 1 分区間は「KVS に届いた最新の断片のプロデューサー時刻が区間の終わりを越えた」か「区間の終わりから `MAX_LATE_SECONDS`(既定 720 秒)過ぎた」ときだけ処理する。満たさなければ止めて次の起動を待つ。区間の処理は 1 回だけ。同じプロデューサー時刻の重複断片は 1 つにまとめる
- 理由: kvssink は回線復旧後にバッファを古い順に送る(4 分の遮断試験で逆転 0、重複 0)。遅れて届いた断片を後から探して作り直す方式より単純で、「処理済み位置より前はすべて確定」を保てる
- 構想.md との差: 「1回の起動での流れ」の 2 と 3 の間に、この判定が入る。配信停止中やオフライン中は、処理済み位置が現在より約 `MAX_LATE_SECONDS` 遅れる(その範囲はビューワーが KVS から再生する)

### GetImages をやめ、キーフレームを Lambda 内でデコードする(B 案、2026-10-24)

- 決めたこと: 動画退避は、HLS の断片を連結した clip のキーフレームからスプライトを作る。物体検出は、S3 の `clip.mp4` を読んでキーフレームをデコードし推論する。デコードは FFmpeg を HEVC/H.264 のデコーダだけでビルドした PyAV(`lambdas/common/pyav_min`、LGPL)
- 理由: GetImages(1 枚 $0.00001)がスプライト用と検出用で 1 台・月 $52.7 かかり、総額の半分以上だった。B 案で変わる項目は $59.18 → $6.77。PyPI の PyAV は GPL のライブラリを含み、detector の zip が 272MB で上限を超えるため最小ビルドにした(197MB)。GetImages が途中から全コマ `MEDIA_ERROR` を返し続ける事象もあった
- 構想.md との差: 「ffmpeg を使わない案を先に試す」から、デコーダだけを同梱する形に変更。物体検出は動画退避の処理済み位置を越えない(検出は動画より 0〜1 分遅れる)。スプライトのコマと検出の `ts` は、秒ちょうどではなくその秒のキーフレームの時刻。動画退避が失敗した区間だけ GetImages を予備に使う
- 注意: H.265 には特許プールがある。商用化の前に確認する

### 物体検出は YOLOX-Tiny INT8、入力幅 640、arm64 1024MB(2026-10-24)

- 決めたこと: YOLOX-Tiny(Apache-2.0)を ONNX Runtime の INT8 静的量子化(S8S8)で、入力 640×360、arm64、1024MB
- 理由: AGPL の Ultralytics を避けた。arm64 では INT8 で約 3 倍速い(x86 では効果が小さい)。640 は 416 より推論が約 2.2 倍かかるが、person の再現率が 0.61 → 0.94(YOLOX-S を仮の正解とした簡易比較)。1 区間 約 9.5 秒で 60 秒に十分収まる
- 構想.md との差: なし(「超軽量な汎用物体検出モデル」の具体化)

## 機能追加

### PTZ は IoT Core 経由、エミュレーターはデジタル PTZ(2026-10-24)

- 決めたこと: ビューワー → API → IoT Core(cmd トピック)→ エッジ → ONVIF PTZ。エミュレーターは元映像からの切り出し窓を動かす疑似 PTZ。位置はシャドウで返す
- 理由: 今後の作業で PTZ が要る。エミュレーターで実機なしに検証できるようにする
- 構想.md との差: 構想には PTZ がなかった(追加機能)
