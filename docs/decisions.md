# 決定事項の記録

[構想.md](../構想.md) の設計から、検証を進める中で決めたこと・変えたことを、日付順ではなくテーマごとに残す。
各項目は「決めたこと」「理由(実測や調査の根拠)」「構想.md との差」の順。細かい仕様は [contracts.md](contracts.md) と各コンポーネントの README。

## エッジ

### H.265 をそのまま KVS へ送るパイプライン(2026-10-24)

- 決めたこと: `rtspsrc ! rtph265depay ! h265parse ! video/x-h265,stream-format=hvc1,alignment=au ! h265timestamper ! kvssink`
- 理由: RTSP から取り出したフレームには DTS がなく、kvssink がキーフレームを捨てて断片が 1 つもできなかった。`h265timestamper` で解決。kvssink はコーデックプライベートデータを caps の `codec_data` からしか取らないため `hvc1` の指定が必須
- 構想.md との差: なし(再エンコードしない方針のまま)

### 映像形式はカメラごとに H.265 / H.264 を選べる。既定は H.265(2026-10-24)

- 決めたこと: 既定は H.265 のまま(ライブも録画も)。ビューワーのカメラ設定から H.264 に切り替えられる(配信は動いたまま数秒途切れ、以降の録画がその形式)。
  エッジはシャドウの desired `codec` を見て ONVIF でカメラのエンコーダーを切り替え、パイプラインを組み直す。区間の途中で切り替わった 1 分は部分ごとの clip(`clip.mp4`、`clip.1.mp4` …)にする
- 理由: H.265 を再生できないブラウザ(Firefox など)向けに互換性を選べるようにする。同じ画質で H.264 は約 1.6 倍のビットレートで、
  帯域・取り込み・保存の費用が増える(比較測定は [codec.md](codec.md))
- 構想.md との差: 「カメラ側で H.265 の VBR」を既定として残し、H.264 を選択肢に加えた。エッジは再エンコードしない(カメラの設定を変える)

### 回線断はメモリのバッファまで(2026-10-24)

- 決めたこと: kvssink のメモリ上のバッファを約 10 分ぶんに設定し、回線断ではパイプラインを再起動しない。ディスクへの退避はしない
- 理由: ディスク退避は録画・再送の仕組みを自前で作ることになり、エッジが厚くなりすぎる。10 分を超える回線断は欠落として許容
- 構想.md との差: 「エッジでバッファリングしない」から、kvssink の既存機能の設定範囲だけ許容に変更

### ライブの低遅延化のためならエッジが少し厚くなってもよい(2026-10-24)

- 決めたこと: KVS WebRTC(シグナリングチャネル)によるライブ配信を調査・試作する。エッジに WebRTC の送信部品が増えるのは許容
- 理由: HLS のライブは数秒遅れ、PTZ の操作感が悪い。低遅延のメリットがエッジの複雑さを上回る
- 構想.md との差: ライブの経路に WebRTC が加わる(調査結果は [webrtc.md](webrtc.md))
- 実装の方針(2026-10-24): ライブは WebRTC を基本にし、失敗したら HLS に切り替える。シグナリングチャネルは 1 カメラ 1 本で、なるべく Terraform で管理する
- 実装(2026-10-24): master(C SDK v1.20.0)を既存のエッジのイメージに入れ、エージェントがカメラごとに子プロセスとして起動・監視する(録画の runner と同じバックオフ。録画とは別プロセスなので回線断のバッファには触らない)。
  視聴者ごとに offer の並びを見て main(H.265)か sub(H.264)を流し、両方の視聴者が同時にいれば両方の RTSP を読む。ビューワーは API が署名した WSS URL で接続し、10 秒以内に映像が出なければ HLS に切り替える。PTZ は WebRTC のライブ再生中だけ操作できる。
  契約は [contracts.md](contracts.md)(シャドウの `webrtc`、status の `webrtc`、`GET /api/cameras/{id}/webrtc`)

### シグナリングチャネルは Terraform の awscc プロバイダーで作る(2026-10-24)

- 決めたこと: `{p}-{camera_id}` のチャネルを `awscc_kinesisvideo_signaling_channel`(Cloud Control API の `AWS::KinesisVideo::SignalingChannel`)でカメラごとに作る。IAM(エッジの ConnectAsMaster、API の ConnectAsViewer など)はチャネルの ARN を個別に指定する
- 理由: hashicorp/aws(6.70.0 時点)にはシグナリングチャネルのリソースがない。CloudFormation の型は Cloud Control で FULLY_MUTABLE(作成・更新・削除・一覧に対応)なので、awscc で state に載り、destroy で消える。エッジに CreateSignalingChannel を許して作らせる案は、削除が Terraform の外になるので採らなかった
- 注意: awscc は default_tags を持たないので、`Project` / `ManagedBy` のタグをリソースに直接付けている

### コーデックは H.265 を基本にし、H.264 にも切り替えられるようにする(2026-10-24)

- 決めたこと: ライブも録画も、可能な限り H.265。録画は H.265 のまま。ただし設定で H.264 / H.265 を切り替えられるようにする。WebRTC で H.265 を受けられないブラウザには、カメラの sub(H.264)を見せる
- 理由: H.265 での帯域とストレージの削減は、この検証の中心の仮説。一方で、ブラウザの H.265 対応(特に WebRTC と Firefox)に穴がある
- 追加(2026-10-24): ユーザーがビューワーからカメラごとに H.264 / H.265 を選び、配信を動いたまま切り替えられるようにする(以降の録画もその形式。過去の録画はそのまま)。H.265 を再生できない環境向けの逃げ道
- 確認中: H.264 と H.265 の同画質でのビットレートと費用の比較([codec.md](codec.md))、ブラウザごとの対応状況と、対応するユーザーの割合の概算([browser-hevc.md](browser-hevc.md))

## クラウドの処理

### 区間の確定はウォーターマーク方式(2026-10-24)

- 決めたこと: 1 分区間は「KVS に届いた最新の断片のプロデューサー時刻が区間の終わりを越えた」か「区間の終わりから `MAX_LATE_SECONDS`(既定 720 秒)過ぎた」ときだけ処理する。満たさなければ止めて次の起動を待つ。区間の処理は 1 回だけ。同じプロデューサー時刻の重複断片は 1 つにまとめる
- 理由: kvssink は回線復旧後にバッファを古い順に送る(4 分の遮断試験で逆転 0、重複 0)。遅れて届いた断片を後から探して作り直す方式より単純で、「処理済み位置より前はすべて確定」を保てる
- 構想.md との差: 「1回の起動での流れ」の 2 と 3 の間に、この判定が入る。配信停止中やオフライン中は、処理済み位置が現在より約 `MAX_LATE_SECONDS` 遅れる(その範囲はビューワーが KVS から再生する)

### GetImages をやめ、キーフレームを Lambda 内でデコードする(B 案、2026-10-24)

- 決めたこと: 動画退避は、HLS の断片を連結した clip のキーフレームからスプライトを作る。物体検出は、S3 の `clip.mp4` を読んでキーフレームをデコードし推論する。デコードは FFmpeg を HEVC/H.264 のデコーダだけでビルドした PyAV(`lambdas/common/pyav_min`、LGPL)
- 理由: GetImages(1 枚 $0.00001)がスプライト用と検出用で 1 台・月 $52.7 かかり、総額の半分以上だった。B 案で変わる項目は $59.18 → $6.77。PyPI の PyAV は GPL のライブラリを含み、detector の zip が 272MB で上限を超えるため最小ビルドにした(197MB)。GetImages が途中から全コマ `MEDIA_ERROR` を返し続ける事象もあった
- 構想.md との差: 「ffmpeg を使わない案を先に試す」から、デコーダだけを同梱する形に変更。物体検出は動画退避の処理済み位置を越えない(検出は動画より 0〜1 分遅れる)。スプライトのコマと検出の `ts` は、秒ちょうどではなくその秒のキーフレームの時刻。動画退避が失敗した区間だけ GetImages を予備に使う
- 注意: H.265 には特許プールがある。商用化の前に確認する

### 物体検出は YOLOX-Tiny INT8、入力幅 640、arm64 1024MB(2026-10-24)

- 決めたこと: YOLOX-Tiny(Apache-2.0)を ONNX Runtime の INT8 静的量子化(S8S8)で、入力 640×360、arm64、1024MB
- 理由: AGPL の Ultralytics を避けた。arm64 では INT8 で約 3 倍速い(x86 では効果が小さい)。640 は 416 より推論が約 2.2 倍かかるが、person の再現率が 0.61 → 0.94(YOLOX-S を仮の正解とした簡易比較)。1 区間 約 9.5 秒で 60 秒に十分収まる
- 構想.md との差: なし(「超軽量な汎用物体検出モデル」の具体化)

## 機能追加

### PTZ は IoT Core 経由、エミュレーターはデジタル PTZ(2026-10-24)

- 決めたこと: ビューワー → API → IoT Core(cmd トピック)→ エッジ → ONVIF PTZ。エミュレーターは元映像からの切り出し窓を動かす疑似 PTZ。位置はシャドウで返す
- 理由: 今後の作業で PTZ が要る。エミュレーターで実機なしに検証できるようにする
- 構想.md との差: 構想には PTZ がなかった(追加機能)

## 台数

### 大きな台数での追加検証はしない(2026-10-24)

- 決めたこと: 数十台以上での実測はしない。Lambda の同時実行の上限(このアカウントは 10)の引き上げ申請もしない。検証は環境を 1 つずつ動かす
- 理由: 構想.md の論点「台数が増えたときの呼び出し数」「KVS の上限」は、机上の調査と 10 台の実測で答えが出た([scale.md](scale.md))。1 台あたりの呼び出し数は台数によらず一定で、1 台の実測から費用を見積もってよい。作りの問題は Lambda の環境変数 4 KB、シャドウ 8 KB、`GET /api/cameras` の 3 つで、いずれも作りの一部の変更で越えられる。同時実行の上限 10 はアカウントの設定で、作りの問題ではない
- 注意: 同時実行の 10 は API の Lambda と全環境で共有している。2 つの環境を同時に動かすと、API が 429 を返すことがある
